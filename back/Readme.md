# 🏡 Backend проекта «База отдыха у моря»

## Введение

В рамках учебной практики вы работаете с **реальным backend-проектом**, максимально приближенным к коммерческой разработке.

Фронтенд (дизайн и логика интерфейса) уже существует.
Ваша задача — **реализовать API** на базе уже зафиксированных моделей данных.

❗ **Важно:**
Модели и схема базы данных **уже заданы и не должны изменяться**, чтобы избежать конфликтов.
Вся ваша работа будет происходить на уровне:

- views (эндпоинты),
- serializers,
- permissions,
- бизнес-логики.

## ⚙️ Подготовка окружения

### 1. Создание `.env` файла

В корне backend-проекта (`back/`) необходимо создать файл `.env`.

Пример:

```env
DJANGO_SECRET_KEY=dev-secret-key
DJANGO_DEBUG=1
DJANGO_ALLOWED_HOSTS=*

POSTGRES_DB=resort
POSTGRES_USER=resort
POSTGRES_PASSWORD=resort
POSTGRES_HOST=db
POSTGRES_PORT=5432
```

⚠️ Это **dev-настройки**, используются только для учебного проекта.

---

### 2. Запуск проекта

В папке `back/` выполните команду:

```bash
docker compose up --build
```

Docker:

- соберёт backend,
- поднимет базу данных,
- выполнит миграции,
- запустит сервер.

---

### 3. Проверка запуска

После запуска откройте в браузере:

- **Swagger UI (документация API)**
  [http://localhost:8000/api/docs/](http://localhost:8000/api/docs/)

- **OpenAPI схема**
  [http://localhost:8000/api/schema/](http://localhost:8000/api/schema/)

Если Swagger открывается — backend работает корректно.

## 🏠 Задача 1. Управление домами и ценами

### Описание задачи

Нужно реализовать административную часть API для управления объектами размещения на базе отдыха (домики/веранды и т.п.):

- администратор может **создавать и редактировать** домики/веранды и их характеристики (описание, площадь, вместимость, активность);
- администратор может **управлять фото** (загрузка, удаление, порядок);
- администратор может **управлять удобствами** (Wi-Fi, камин, парковка и т.д.) и привязкой удобств к домику;
- администратор может **задавать правила ценообразования** (будни/выходные/периоды).

> Модели данных уже подготовлены и менять их не нужно. Ваша задача — API (views/serializers/urls) и логика.

---

### Примерные эндпоинты и доступы

Ниже — рекомендуемый “скелет” эндпоинтов. Вы можете немного менять маршруты, но смысл должен сохраняться.

#### Публичные (без авторизации) — только чтение

- `GET /api/accommodations/` — список активных домиков/веранд (публично)
- `GET /api/accommodations/{id}/` — детали домика/веранды (публично)

> Публичные эндпоинты должны возвращать только `is_active=true`.

#### Админские (только для администратора) — управление

- `POST /api/admin/accommodations/` — создать домик/веранду
- `PATCH /api/admin/accommodations/{id}/` — частично обновить
- `DELETE /api/admin/accommodations/{id}/` — **желательно не удалять физически**, а делать `is_active=false` (см. рекомендации)

**Удобства:**

- `GET /api/admin/amenities/` — список удобств
- `POST /api/admin/amenities/` — создать удобство
- `PATCH /api/admin/amenities/{id}/` — изменить
- `DELETE /api/admin/amenities/{id}/` — удалить (если нигде не используется)

**Привязка удобств к домику:**

- `PUT /api/admin/accommodations/{id}/amenities/` — перезаписать список удобств у домика
  Тело: `{ "amenity_ids": ["...", "..."] }`

**Фото домика:**

- `POST /api/admin/accommodations/{id}/images/` — загрузить фото (multipart/form-data)
- `DELETE /api/admin/accommodations/{id}/images/{image_id}/` — удалить фото
- `PATCH /api/admin/accommodations/{id}/images/{image_id}/` — изменить порядок
  Тело: `{ "order": 2 }`

**Цены:**

- `GET /api/admin/accommodations/{id}/price-rules/` — правила цен домика
- `POST /api/admin/accommodations/{id}/price-rules/` — создать правило
- `PATCH /api/admin/price-rules/{rule_id}/` — обновить правило
- `DELETE /api/admin/price-rules/{rule_id}/` — удалить/деактивировать правило

---

### Особенности и рекомендации

#### 1) Изображения: оптимизация (обязательно)

Фотографии не должны “съедать” память и диск.

При загрузке изображения:

- конвертируйте в **WebP**;
- ограничивайте размеры (например, максимум 1920px по длинной стороне);
- сжимайте (качество 70–85 обычно достаточно);
- сохраняйте уже оптимизированный файл.

**Подсказка по реализации:**

- используйте `Pillow`;
- обрабатывайте изображение **до сохранения** в `ImageField`;
- имя файла лучше генерировать заново, чтобы не сохранять огромные оригиналы.

#### 2) `is_active` вместо удаления

Для “удаления” домика лучше:

- не удалять запись из БД,
- а выставлять `is_active=false`.

Так вы избежите проблем с бронированиями, историей и ссылками.

#### 3) Логика цен должна быть расширяемой

Не пытайтесь сразу предусмотреть всё (сезоны, промокоды, скидки и т.п.).
Сейчас достаточно:

- WEEKDAY / WEEKEND
- PERIOD (праздники/периоды)
- возможность приоритета (чтобы период перекрывал базовую цену)

#### 4) Swagger — часть задачи

В Swagger должно быть понятно:

- какие эндпоинты админские, а какие публичные;
- какие поля обязательны;
- какие коды ошибок возможны.

Рекомендуется:

- описывать ошибки 400/403/404/409;
- добавлять краткое описание бизнес-логики в `description`.

#### 5) Валидации, которые стоит сделать сразу

- `capacity_min <= capacity_max`
- `area_m2` не отрицательное
- `PriceRule`:
  - для PERIOD: `date_from` и `date_to` обязательны и `date_from <= date_to`
  - для WEEKDAY/WEEKEND: даты должны быть пустыми (или игнорироваться)

## 📅 Задача 2. Бронирование

### Описание задачи

Нужно реализовать пользовательский сценарий бронирования домика/веранды:

- пользователь выбирает объект размещения;
- смотрит **календарь доступности** (какие даты свободны) и **стоимость по дням**;
- оформляет бронь;
- «оплачивает» (в учебном проекте — **симуляция**, всегда успех);
- может отменить бронь;
- видит историю своих бронирований.

> Модели данных уже подготовлены и менять их не нужно. Ваша задача — API (views/serializers/urls) и логика.

---

### Примерные эндпоинты и доступы

#### Публичные (без авторизации) — просмотр доступности

- `GET /api/accommodations/{id}/availability/` — календарь доступности + цены

**Query-параметры (рекомендация):**

- `date_from=YYYY-MM-DD`
- `date_to=YYYY-MM-DD`

**Пример ответа (рекомендуемый формат «по дням», удобен фронту):**

```json
{
  "accommodation_id": "...",
  "date_from": "2026-03-01",
  "date_to": "2026-03-15",
  "days": [
    { "date": "2026-03-01", "is_available": true, "price": "6500.00" },
    { "date": "2026-03-02", "is_available": true, "price": "6500.00" },
    { "date": "2026-03-03", "is_available": false, "price": "6500.00" }
  ]
}
```

> `price` возвращаем всегда, даже если день занят (это упрощает отрисовку календаря и сравнение цен).

#### Пользовательские (нужна авторизация) — бронирования

- `POST /api/bookings/` — создать бронь (и запустить симуляцию оплаты)
- `GET /api/me/bookings/` — история бронирований текущего пользователя
- `GET /api/bookings/{id}/` — детали бронирования (только владелец)
- `POST /api/bookings/{id}/cancel/` — отменить бронь (только владелец)

**Пример `POST /api/bookings/` (тело запроса):**

```json
{
  "accommodation_id": "...",
  "check_in": "2026-03-10",
  "check_out": "2026-03-12",
  "guests_count": 2,
  "comment": "Хотим заезд после 18:00"
}
```

**Доступы (кратко):**

- создание/просмотр «моих» броней — только авторизованный пользователь;
- просмотр/отмена конкретной брони — только владелец брони (или админ, если вы это добавите).

#### Админские (опционально)

- `GET /api/admin/bookings/` — список всех броней
- `PATCH /api/admin/bookings/{id}/` — изменение статуса/комментариев

> Админские эндпоинты можно сделать как «плюс» — если успеваете.

---

### Особенности и рекомендации

#### 1) Календарь доступности + цены — главный кусок задачи

Календарь должен учитывать:

- занятость (существующие брони со статусами, которые блокируют даты);
- цену на каждый день с учётом правил (будни/выходные/периоды).

**Рекомендация по диапазону:**

- если фронт не передал диапазон — возвращайте, например, 30–60 дней вперёд.

#### 2) Проверка пересечения дат (обязательно)

При создании бронирования убедитесь, что выбранный период не пересекается с уже занятыми датами.

Рекомендуемые ответы:

- `409 Conflict` — если даты заняты (конфликт бронирования);
- `400 Bad Request` — если `check_in >= check_out` или некорректные данные.

> Даты обычно считаются так: `check_in` включительно, `check_out` **не включительно**.

#### 3) Симуляция оплаты

В учебном проекте оплата **всегда успешна**.

Варианты реализации (выберите один):

- **простой:** при `POST /api/bookings/` сразу ставить статус `CONFIRMED`;
- **чуть реалистичнее:**
  - создаём бронь в статусе `NEW`,
  - «платёж» отдельным эндпоинтом `POST /api/bookings/{id}/pay/` переводит в `CONFIRMED`.

> Для практики обычно удобнее первый вариант: меньше эндпоинтов — быстрее собрать MVP.

#### 4) Статусы бронирования должны быть явными

Используйте только значения:

- `NEW`
- `CONFIRMED`
- `CANCELED`
- `COMPLETED`

**Подсказка:**

- при отмене пользователем → `CANCELED`;
- «COMPLETED» можно не автоматизировать, если не успеваете (оставить админом или как future work).

#### 5) Расчёт стоимости

Минимально достаточно:

- посчитать сумму по дням на основе календаря цен;
- записать в `total_price`.

Ошибки, которые стоит ловить:

- цена на день не найдена (если у вас такое возможно) → `500` или `400` с понятным сообщением;
- домик не активен → `404` или `409` (на ваш выбор, но описать в Swagger).

#### 6) Swagger — часть задачи

В Swagger должно быть понятно:

- как получить календарь доступности;
- как создать бронь;
- какие статусы возможны;
- какие ошибки возвращаются (400/401/403/404/409).

## 🔔 Задача 3. Администрирование и уведомления

### Описание задачи

Нужно реализовать административные сценарии безопасности и коммуникации:

1. **Blacklist по номеру телефона**

- если пользователь «плохой» (разгромил домик, нарушал правила) — администратор добавляет его телефон в blacklist;
- дальше любые действия, связанные с бронированием, для этого телефона должны быть **ограничены**.

2. **Уведомления в Telegram**

- пользователю: например, «завтра заезд», «бронь подтверждена», «бронь отменена»;
- администратору/работнику базы: например, «завтра заняты домики №1 и №3».

> Это не страшная задача: можно сделать MVP очень простым способом, главное — понятная архитектура и рабочий результат.

---

### Примерные эндпоинты и доступы

#### Админские (только администратор) — blacklist

- `GET /api/admin/blacklist/` — список телефонов в blacklist
- `POST /api/admin/blacklist/` — добавить телефон
- `DELETE /api/admin/blacklist/{id}/` — удалить из blacklist

**Пример `POST /api/admin/blacklist/`:**

```json
{
  "phone": "+79991234567",
  "reason": "Разгромил домик"
}
```

#### Пользовательские (нужна авторизация) — привязка Telegram

- `POST /api/me/telegram/link/` — привязать Telegram к пользователю
- `POST /api/me/telegram/unlink/` — отвязать Telegram

> Реализацию привязки можно сделать упрощённо: хранить `chat_id` у пользователя или в отдельной таблице.

#### Системные/админские (только администратор) — отправка уведомлений

- `POST /api/admin/notifications/test/` — тестовая отправка сообщения в TG (на заданный `chat_id`)
- `POST /api/admin/notifications/daily/` — отправить «дайджест на завтра» администратору (занятые домики)

> Эти эндпоинты допустимы даже если вы не сделали полноценный планировщик — они помогают проверить отправку.

---

### Особенности и рекомендации

#### 1) Как ограничивать бронирование для blacklist

Минимально достаточно:

- при создании бронирования (`POST /api/bookings/`) проверять, что телефон пользователя **не в blacklist**;
- если в blacklist — возвращать `403 Forbidden` с понятным сообщением.

**Рекомендация:**

- блокируйте именно _операции бронирования_, а не весь доступ к API (чтобы пользователь мог хотя бы посмотреть историю или профиль, если нужно).

#### 2) Telegram-уведомления — как это обычно делают (простым языком)

Telegram позволяет отправлять сообщения боту через HTTP-запрос.

Вам нужно 2 вещи:

1. **Токен бота** (выдаёт @BotFather)
2. **chat_id** — идентификатор чата, куда отправлять сообщения

Самый простой сценарий привязки (MVP):

- пользователь пишет вашему боту команду `/start <код>`
- бот пересылает этот код на backend
- backend связывает `chat_id` с пользователем

#### 3) Как отправлять уведомления «завтра заезд»

Есть 3 уровня сложности — выберите любой:

**Уровень A (самый простой, подходит первокурснику):**

- сделать endpoint `POST /api/admin/notifications/daily/`
- админ вызывает его вручную
- backend ищет брони на завтра и отправляет сообщения

**Уровень B (чуть лучше):**

- добавить Django management command, например `python manage.py send_daily_notifications`
- админ запускает команду вручную или через cron

**Уровень C (на будущее/если успеваете):**

- добавить Celery + Celery Beat и расписание

Для практики **уровня A или B достаточно**.

#### 4) Какие брони учитывать

Для уведомлений и «занятости» обычно учитывают статусы:

- `CONFIRMED` (точно занято)
- иногда `NEW` (если вы хотите держать бронь «в оплате», но у нас оплата симулируется)

`CANCELED` и `COMPLETED` учитывать не нужно.

#### 5) Шаблоны сообщений

Не усложняйте, достаточно таких сообщений:

- Пользователю: `"Напоминание: завтра заезд в домик «{title}». Даты: {check_in}–{check_out}."`
- Админу: `"Завтра заняты: Домик 1, Домик 3."` (+ можно добавить список броней)

#### 6) Где хранить настройки Telegram

- токен бота хранить в `.env` (например, `TG_BOT_TOKEN=...`)
- `chat_id` хранить в БД

#### 7) Swagger — часть задачи

В Swagger должно быть понятно:

- как управлять blacklist;
- как привязать Telegram;
- какие уведомления есть и как их проверить.

Рекомендуемые ошибки:

- `403 Forbidden` — попытка бронирования из blacklist
- `400 Bad Request` — неверный формат телефона / не хватает данных
- `502 Bad Gateway` (или `500`) — если Telegram API не отвечает (можно вернуть 500 с понятным сообщением)

---

✅ Минимальный результат (MVP), который считается успешным:

- admin может добавить телефон в blacklist;
- пользователь из blacklist не может создать бронирование;
- есть способ привязать `chat_id` пользователю (пусть даже вручную);
- можно отправить тестовое сообщение в Telegram и получить уведомление.
